xFabric uses a layered configuration system with six distinct config types, each delivered through a different path depending on the deployment environment.

## Config types

| Type | Delivery | Example |
|---|---|---|
| **Chart-wired static** | Helm values → env vars | `TOPOLOGY_BATCH_SIZE`, service ports |
| **Chart-wired secrets** | Helm values → K8s secrets → env vars | Database connection strings, API keys for external services |
| **Auto-generated persisted secrets** | Generated at install, stored in Secret Manager | JWT signing keys, internal service tokens |
| **Feature flags** | Control plane API → runtime reload | `WORLD_MODEL_REBUILD_ENABLED`, product toggles |
| **Extra config** | Control plane API | Customer-specific overrides |
| **Runtime-delivered secrets** | Secret Manager → sidecar injection | LLM provider keys, OAuth client secrets |

## Delivery paths by environment

<Tabs>
  <Tab title="Production (K8s)">
    Config flows through Helm charts with a **SplitValues** boundary separating secrets from non-secret config. Per-cloud assemblers handle GKE/EKS/AKS differences.

    Secrets are stored in the cloud provider's secret manager (GCP Secret Manager, AWS Secrets Manager, Azure Key Vault) and injected into pods at runtime.
  </Tab>
  <Tab title="Local dev (k3d)">
    Docker Compose with environment files. Secrets are stored in `.env` files that are not committed to source control.
  </Tab>
  <Tab title="Production VM">
    Docker Compose with environment files and a simplified secret delivery path.
  </Tab>
</Tabs>

## Control plane APIs

These endpoints manage runtime configuration:

| Method | Path | Description |
|---|---|---|
| `PUT` | `/server-admin/config-states/` | Update config state |
| `POST` | `/license/k8s-config/apply/` | Apply Kubernetes config |
| `PUT` | `/license/feature-flags/` | Update feature flags |
| `PUT` | `/license/config/` | Update license config |
| `POST` | `/server-admin/reconcile/` | Reconcile config state |

## Adding a new environment variable

When adding a new config value, use this decision tree:

1. **Is it a secret?** → Use chart-wired secrets or runtime-delivered secrets
2. **Does it change per customer?** → Use extra config via control plane API
3. **Is it a product toggle?** → Use feature flags
4. **Is it static infrastructure config?** → Use chart-wired static values

For chart-wired values, add the variable to the Helm chart's `values.yaml` and reference it in the deployment template. The value flows from Helm → ConfigMap/Secret → env var in the pod.
