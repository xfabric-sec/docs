Agent Memory models retrieval as a Markov Decision Process (MDP) that iteratively refines results using multiple search strategies.

## Hybrid search

Every retrieval combines three search strategies and fuses their results:

| Strategy | How it works | Storage backend |
|---|---|---|
| **Semantic search** | Vector similarity using embeddings | ChromaDB or pgvector |
| **BM25** | Keyword-based ranking for exact term matches | File-based or PostgreSQL |
| **Cue anchors** | Contextual keywords extracted during ingestion | File-based or PostgreSQL |

Results from all strategies are fused using Reciprocal Rank Fusion (RRF).

## Policy-driven MDP

The retrieval policy decides at each step which action to take:

| Action | Description |
|---|---|
| **Expand** | Broaden the search with related terms |
| **Refine query** | Narrow results by reformulating the query |
| **Decompose query** | Break a complex query into sub-questions |
| **Terminate** | Return the current results when confidence is high enough |

The MDP runs for up to 5 steps (configurable via `max_steps`), with an initial fetch of 15 memories per step.

## Retriever types

Agent Memory ships with multiple retriever implementations:

| Retriever | Description |
|---|---|
| **policy** (default) | Full MDP with all four actions |
| **semantic** | Single-shot vector similarity search |
| **query_reformulation** | Reformulates the query before searching |
| **plan_based** | Plans a multi-step retrieval strategy |
| **prompted_policy** | Policy-driven with custom prompt templates |
| **hybrid_retriever** | Direct hybrid search without MDP |

Override the retriever per request:

```bash
curl -X POST https://api.xfabric.io/v1/memory/retrieve \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query": "auth flow", "collection": "my-project", "retriever": "semantic"}'
```

## Retrieve API

### Basic retrieval

```bash
curl -X POST https://api.xfabric.io/v1/memory/retrieve \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "query": "authentication flow",
    "collection": "my-project",
    "k": 10,
    "include_graph": true
  }'
```

**Response:**

```json
{
  "query": "authentication flow",
  "memories": [
    {
      "memory_id": "mem_abc",
      "title": "JWT authentication in admin-backend",
      "text": "The admin-backend issues JWTs after validating...",
      "document_id": "doc_123",
      "query_similarity": 0.89
    }
  ],
  "steps_taken": 3,
  "scanned_count": 45,
  "graph": {
    "nodes": [...],
    "edges": [...]
  }
}
```

## Question answering

The `/ask` endpoint combines retrieval with LLM-based answer generation:

1. Retrieves relevant memories using the configured retriever
2. Passes memories as context to the QA model (default: gpt-5.4-mini, max 4000 context chars)
3. Generates a grounded answer with citations
4. A judge model (default: gpt-5.5) evaluates answer quality

```bash
curl -X POST https://api.xfabric.io/v1/memory/ask \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "question": "What database does the auth service use?",
    "collection": "my-project",
    "include_memories": true
  }'
```

**Response (when complete):**

```json
{
  "question": "What database does the auth service use?",
  "answer": "The auth service uses PostgreSQL...",
  "context_memories": 8,
  "context_chars": 3200,
  "retrieval_steps": 3
}
```

### Judge API

Evaluate answer quality independently:

```bash
curl -X POST https://api.xfabric.io/v1/memory/judge \
  -H "Authorization: Bearer YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "question": "What database does the auth service use?",
    "expected_answer": "PostgreSQL",
    "generated_answer": "The auth service uses PostgreSQL for user storage."
  }'
```

```json
{
  "is_correct": true,
  "explanation": "The generated answer correctly identifies PostgreSQL..."
}
```

## Memory graph

Memories are connected in a graph structure. When you retrieve with `include_graph: true`, you get the relationship graph:

| Edge type | Meaning |
|---|---|
| `sibling` | Memories from adjacent segments |
| `shared_anchor` | Memories sharing the same cue anchor |
| `same_document` | Memories from the same source document |
| `hierarchical` | Parent-child heading relationships |

Each node includes the memory content plus metadata: `cue_anchors`, `hierarchy_path`, `document_name`, and `query_similarity`.
