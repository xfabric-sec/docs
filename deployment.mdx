title: "Deployment"

Cielara runs inside your own cloud account, so your data stays in infrastructure you own. Your 30-day trial starts as soon as you sign up, and the steps below take you from a new account to a running Cielara instance.

This page mirrors the deploy form section by section. Names in bold are the labels you see in the form, in the order the form shows them.

## Deployment Flow

<Steps>
  <Step title="Sign Up for a Cielara Account">
    Go to [console.cielara.ai/signup](https://console.cielara.ai/signup) and sign up. Enter your details and verify your email. Once your account is created you receive a 30-day trial license and access to the Cielara console.

    If the console shows **Your license is being set up** after you sign in, your trial license is still being issued. This usually takes a few minutes.
  </Step>
  <Step title="Open the Deploy Form">
    Sign in to the Cielara console. A new account with no deployment opens the deploy form directly. You can also reach it from **Deployments** in the sidebar.
  </Step>
  <Step title="Choose Your Cloud">
    Under **Where to deploy**, pick **Google Cloud**, **AWS** or **Azure**. The fields below the picker change to match your cloud, and the **Your deployment** panel on the right summarizes your choices as you go.

    Every deployment needs the same four things from you, whichever cloud you choose:

    | What you provide | Why |
    |---|---|
    | A region and a **Deployment name** | Where Cielara runs and how its resources are named |
    | A credential from a one-time prepare step | How Cielara creates resources in your account |
    | **Infrastructure** choices (optional) | Network, node pools, database and version. Every row shows its current value; the defaults suit most deployments |
  </Step>
  <Step title="Fill in the Form">
    <Tabs>
      <Tab title="GCP">
        ### Where to Deploy

        | Field | Description |
        |---|---|
        | **Project ID** | Your Google Cloud project ID. Find it in the GCP console under **Project info**, or run `gcloud config get-value project`. |
        | **Region** | The region Cielara runs in, for example `us-central1`. Choose the region closest to your team or where your data residency requirements apply. Cannot be changed after deployment. |
        | **Deployment name** | A short lowercase name of up to 25 characters, for example `acme`. Cielara names every resource it creates `cdl-<timestamp>-<name>`. |

        ### Prepare Your Google Cloud Project

        This section creates the service account Cielara deploys with. The **Deployment guide** link in the section header brings you back to this page.

        The apply writes `cielara-key.json`, a Google service account key. Treat it like a password and do not commit it to git.

        You need Terraform 1.7 or later and the `gcloud` CLI, signed in as a project owner.

        1. **Sign in.** Google expires these credentials on its own schedule, so repeat this before every apply.

           ```bash
           gcloud auth login && gcloud auth application-default login
           ```
        2. **Download main.tf.** Enter your Project ID first so the file is pre-filled. Save it into an empty folder. Keep the Terraform state in versioned object storage you own rather than a workstation, because future updates reuse it. The file carries ready-made backend blocks to uncomment.
        3. **Apply.** The apply enables the required APIs, creates the service account with the minimum IAM roles, and writes `cielara-key.json` into the module directory.

           ```bash
           terraform init && terraform apply
           ```
        4. **Upload the key.** Drop `cielara-key.json` on the **Drop cielara-key.json here** target, or click **Browse**.

        Tick **This account was prepared before, or the Terraform state is lost** if you ran an earlier version of the setup or lost the state. The file then adopts what already exists instead of recreating it.

        | Field | Description |
        |---|---|
        | **Drop cielara-key.json here** | The `cielara-key.json` written by the apply. |
        | **Terraform State Storage URL** | Where your prepare run keeps its Terraform state, for example `gs://my-terraform-state-bucket/cielara-prepare/gke`. Filled automatically when the uploaded key file records it. Recorded with the deployment so a later update can find the state. |

        Keep the Terraform state in your own custody. It contains the key, and Cielara never needs it.

          <Accordion title="Network">
            Cielara creates the network unless you fill these fields in.

            Under **Infrastructure**, the **Network** row reads **Cielara creates the VPC, subnet and NAT gateway**. Click **Use my own** to deploy into a network you already own; the row then reads **Using your own network** and the **Your deployment** panel lists it under **Changed from defaults**. To do so, fill in the fields from the handback of Cielara's [`cielara-network`](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-network/google/latest) Terraform module, or from your existing networking. The VPC and subnet fields go together: fill both or neither.

            | Field | Handback key | Description |
            |---|---|---|
            | **VPC** | `vpc_self_link` | The self-link or bare name of the VPC. Must be in the same project as the service account key. |
            | **Subnet** | `gke_subnet_self_link` | The self-link or bare name of a regional subnet in the selected region. It needs private Google access and two secondary ranges, one for pods and one for services. |
            | **Pods range name** | | The subnet's secondary range for pods. Defaults to `pods`. |
            | **Services range name** | | The subnet's secondary range for services. Defaults to `services`. |
            | **NAT egress IP** | `nat_ip` | The network's static Cloud NAT egress IP. Required when the deployment uses managed RabbitMQ, because the broker firewall admits exactly this address. |
            | **Cloud SQL PSA range CIDR** | | The private services access range for Cloud SQL. Defaults to `10.96.0.0/16`. Change it only if that range collides with your network's address space. |

            To provision the network with the module, write a `main.tf` in an empty folder:

            ```hcl
            provider "google" {
              project = "my-gcp-project"
              region  = "us-central1"
            }

            module "cielara_network" {
              source  = "causal-dynamics-lab/cielara-network/google"
              version = "X.Y.Z" # pin the latest version shown on the registry page

              project_id = "my-gcp-project"
              region     = "us-central1" # the region you pick on the deploy form

              # gke_subnet_cidr = "10.10.0.0/20" # default; change if it overlaps
              # pods_cidr       = "10.11.0.0/16" # secondary range for pods
              # services_cidr   = "10.12.0.0/20" # secondary range for services
            }

            output "handback" {
              value = module.cielara_network.handback
            }
            ```

            Then apply and print the values to paste into the form:

            ```bash
            gcloud auth application-default login
            terraform init
            terraform apply
            terraform output -raw handback
            ```

        ### Prepare Your AWS Account

        This section creates the cross-account IAM role Cielara deploys with. No long-lived keys leave your account.

        The download is generated for your Cielara account, so take it from your own form rather than reusing a copy.

        You need Terraform 1.7 or later, run as an IAM admin in the account.

        1. **Authenticate.** Use SSO as below, or static keys with `aws configure`. Either way, set a region.

           ```bash
           aws configure sso
           aws sso login --profile <your-profile>
           export AWS_PROFILE=<your-profile>
           export AWS_REGION=<region>
           ```
        2. **Download main.tf.** The file is pre-filled for your account and the region you picked. Save it into an empty folder. Keep the Terraform state in versioned object storage you own rather than a workstation, because future updates reuse it.
        3. **Apply.** The apply creates the `cielara_eks_deployer` role, trusted only by Cielara's control plane and gated by your Cielara client ID, and writes `cielara-creds.json`.

           ```bash
           terraform init && terraform apply
           ```
        4. **Upload the credentials.** Click **Upload cielara-creds.json**. It fills **Role ARN** and **Terraform State Storage URL**. You can also read the ARN and paste it by hand.

           ```bash
           terraform output -raw role_arn
           ```

        Tick **This account was prepared before, or the Terraform state is lost** if you ran an earlier version of the setup or lost the Terraform state. The file then adopts the existing role instead of recreating it.

        | Field | Description |
        |---|---|
        | **Role ARN** | The ARN of the deployer role, for example `arn:aws:iam::123456789012:role/cielara_eks_deployer`. The account ID in the ARN is the account Cielara deploys into. |
        | **Terraform State Storage URL** | Where your prepare run keeps its Terraform state, for example `s3://my-terraform-state-bucket/cielara-prepare/eks/terraform.tfstate`. Filled from the uploaded file. Recorded with the deployment so a later update can find the state. |

        The Terraform state holds no secret, but keep it in your own custody. Cielara never needs it.

            | **Private subnet ID (AZ 2)** | `private_subnet_ids` | A second private subnet in a different availability zone. |

              region = "us-east-1" # must match the provider block

              # vpc_cidr           = "10.2.0.0/20" # default; change if it overlaps
              # availability_zones = ["us-east-1a", "us-east-1b"] # default: first 2 AZs
              # ha_nat             = false # true = one NAT gateway per AZ
            }

        ### Where to Deploy

        | Field | Description |
        |---|---|
        | **Subscription ID** | Your Azure subscription ID. Find it in the Azure portal under **Subscriptions**, or run `az account show --query id -o tsv`. Enter it first: it pre-fills the `main.tf` download below. |

        ### Prepare Your Azure Subscription

        This section creates the service principal Cielara deploys with.

        The download is generated for your Cielara account, so take it from your own form rather than reusing a copy.

        You need Terraform 1.7 or later, run as a subscription Owner or an identity that can create service principals and subscription-scoped role assignments.

        1. **Authenticate.** Use `az login --use-device-code` instead if no browser is available.

           ```bash
           az login
           az account set --subscription <id>
           ```
        2. **Download main.tf.** With your Subscription ID entered above, the file is pre-filled. Save it into an empty folder. Keep the Terraform state in versioned object storage you own rather than a workstation, because future updates reuse it.
        3. **Apply.** The apply creates the `cielara_aks_deployer` service principal scoped to your subscription and writes `cielara-creds.json`.

           ```bash
           terraform init && terraform apply
           ```
        4. **Upload the credentials.** Click **Upload cielara-creds.json**. It fills **Tenant ID**, **Client ID**, **Client secret** and **Terraform State Storage URL**.

        Tick **This account was prepared before, or the Terraform state is lost** if you ran an earlier version of the setup or lost the Terraform state. An adopted setup keeps its existing client secret, so the credentials file omits it: enter the secret by hand. After `terraform init`, run the discovery script to look up your existing Azure object IDs, then plan and apply as usual.

        ```bash
        .terraform/modules/cielara_prepare/discover-migrate.sh <your-cielara-client-id>
        ```

        | Field | Description |
        |---|---|
        | **Tenant ID** | Your Microsoft Entra ID tenant. Find it in the Azure portal under **Microsoft Entra ID > Overview**, or run `az account show --query tenantId -o tsv`. |
        | **Client ID** | The application (client) ID of the `cielara_aks_deployer` service principal. |
        | **Client secret** | The service principal's secret. `cielara-creds.json` holds it, so treat that file like a password and do not commit it to git. |
        | **Terraform State Storage URL** | Where your prepare run keeps its Terraform state, for example `https://mystorageaccount.blob.core.windows.net/tfstate/cielara-prepare-aks.tfstate`. Filled from the uploaded file. Recorded with the deployment so a later update can find the state. |

        The Terraform state also contains the client secret. Keep it in your own custody. Cielara never needs it.

## Terraform Module Reference

The `main.tf` you download pins a release of Cielara's prepare module for your cloud. The full module documentation is on the Terraform Registry:

| Cloud | Module |
|---|---|
| GCP | [cielara-prepare-gke](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-prepare-gke/google/latest) |
| AWS | [cielara-prepare-eks](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-prepare-eks/aws/latest) |
| Azure | [cielara-prepare-aks](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-prepare-aks/azurerm/latest) |

The form links to the exact version it pinned under **View module docs on the Terraform registry**.

If you bring your own network, the module that provisions it is published separately. Pin an exact version rather than tracking the latest:

| Cloud | Module |
|---|---|
| GCP | [cielara-network/google](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-network/google/latest) |
| AWS | [cielara-network/aws](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-network/aws/latest) |
| Azure | [cielara-network/azurerm](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-network/azurerm/latest) |
