Cielara runs inside your own cloud account, so your data stays in infrastructure you own. Your 30-day trial starts as soon as you sign up, and the steps below take you from a new account to a running Cielara instance.

The deploy form is a five-step wizard: **Cloud**, **Target**, **Prepare**, **Infrastructure** and **Review**. This page follows it step by step. Names in bold are the labels you see in the form.

## Before You Start

You run two small Terraform configurations from your own machine: one that creates the identity Cielara deploys with, and one that creates the network Cielara deploys into. You need:

| What | Why |
|---|---|
| Terraform 1.7 or later | Runs the prepare and network configurations. [Install Terraform](https://developer.hashicorp.com/terraform/install) |
| Your cloud's CLI, signed in with admin rights | Terraform uses its credentials. [gcloud](https://cloud.google.com/sdk/docs/install), [AWS CLI](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html) or [Azure CLI](https://learn.microsoft.com/cli/azure/install-azure-cli) |
| A GCP project, AWS account or Azure subscription | Where Cielara runs |

`terraform version` and your CLI's version command (`gcloud version`, `aws --version`, `az version`) show whether you have them.

### Where the Files Go

The form names one folder per deployment, with a subfolder for each Terraform configuration. Each holds its own `main.tf` and Terraform state:

```
~/cielara/<deployment-name>/prepare/   the prepare configuration
~/cielara/<deployment-name>/network/   the network configuration
```

Every command the form shows starts with its own `cd` into the right folder, so you can paste it into any terminal. Keep both folders: re-applies and teardown need the state they hold.

Your browser saves each download wherever it is set to save files. The form's move commands use `<download-folder>` for that location. Replace it before you run the command, usually with `~/Downloads`.

<Note>
On Windows the form shows PowerShell commands instead, marked with a `PS>` prompt. They use `$HOME\cielara\<deployment-name>\...` paths, and each command in a line runs only if the one before it succeeded. Run them in PowerShell, not Command Prompt.
</Note>

        ### Prepare Your GCP Project

        This step creates the service account Cielara deploys with. You need Terraform 1.7 or later and the `gcloud` CLI, signed in as a project owner.

        1. **Sign in to your cloud.** Google expires these credentials on its own schedule, so repeat this before every apply.

           ```bash
           gcloud auth login && gcloud auth application-default login
           ```

           Then check the project. The form fills in your **Project ID**.

           ```bash
           gcloud projects describe <project-id>
           ```

           If it prints the project, the ID is right and your account can see it. An error such as `does not have permission to access projects instance` means the Project ID or the signed-in account is wrong. Fix it before you apply: Terraform fails the same way, only later.
        2. **Make a folder for this deployment.**

           ```bash
           mkdir -p ~/cielara/<name>/prepare && cd ~/cielara/<name>/prepare
           ```
        3. **Download main.tf into it.** Click **Download main.tf**. The file is pre-filled with your project and region. Then move it into the folder:

           ```bash
           mv <download-folder>/main.tf ~/cielara/<name>/prepare/
           ```
        4. **Apply.** The apply enables the required APIs, creates the service account with the minimum IAM roles, and writes `cielara-key.json`.

           ```bash
           cd ~/cielara/<name>/prepare && terraform init && terraform apply
           ```

           By default Terraform keeps its state in this folder. This is not recommended: the state exists only on this machine, and it holds the service account's private key. Keep it in a GCS bucket you own instead. `main.tf` carries ready-made `backend` blocks: uncomment the one you want before `terraform init`. If you already applied with local state, run `terraform init -migrate-state` after uncommenting it.
        5. **Upload the cielara-key.json it writes.** It is in `~/cielara/<name>/prepare`. Drop it on **Drop cielara-key.json here**, or click **Browse**. Treat the file like a password and do not commit it to git.

        The key file also records where the Terraform state lives. Click **Enter manually** to see or change it:

        | Field | Description |
        |---|---|
        | **Terraform State Storage URL** | Where your prepare run keeps its state: `local`, or a bucket such as `gs://acme-inc-tfstate/cielara-prepare/gke`. Recorded with the deployment so a later update can find the state. |

        ### Infrastructure

        #### Network

        Cielara deploys into a network you own. The form gives you a pre-filled Terraform file for Cielara's [`cielara-network`](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-network/google/latest) module. It creates a VPC, a regional subnet with pods and services ranges, private Google access, and Cloud NAT with a static egress IP.

        1. **Make a folder for the network.** It sits next to the prepare folder, not inside it: the network is its own Terraform configuration with its own state.

           ```bash
           mkdir -p ~/cielara/<name>/network && cd ~/cielara/<name>/network
           ```
        2. **Download main.tf into it.** Click **Download main.tf**. The file is pre-filled with your project and region. Move it into the network folder:

           ```bash
           mv <download-folder>/main.tf ~/cielara/<name>/network/
           ```

           If your browser saved it as `main (1).tf` because the prepare `main.tf` was still in the download folder, move that file instead.
        3. **Apply it and write its output.**

           ```bash
           cd ~/cielara/<name>/network && terraform init && terraform apply && terraform output -raw handback > cielara-network.json
           ```
        4. **Upload cielara-network.json.** It is in `~/cielara/<name>/network`. The form lists the values it read from the file, and **Review** shows them again.

        The upload is refused, with the reason, when the file:

        - is empty. The command ran before the apply finished, or the apply failed. Terraform printed why in your terminal
        - describes a network in a different project or region than the **Target** step
        - is missing a value, or has a value Cielara cannot use. Nothing from the file is kept

        **Already have a network made some other way?** Write the same JSON by hand and upload it:

        ```json
        {
          "project_id": "acme-inc-prod",
          "region": "us-central1",
          "vpc_self_link": "projects/acme-inc-prod/global/networks/acme-vpc",
          "gke_subnet_self_link": "projects/acme-inc-prod/regions/us-central1/subnetworks/acme-subnet",
          "pods_range_name": "pods",
          "services_range_name": "services",
          "nat_ip": "203.0.113.10"
        }
        ```

        The network must meet the same contract the module produces. Cielara checks it before the deploy starts:

        - A regional subnet in the deploy region and the deploy project. Shared VPC host and service projects are not supported
        - Two secondary ranges on that subnet, one for pods and one for services. The pods range needs a `/24` per node of free space
        - Private Google access enabled on the subnet
        - Working egress (Cloud NAT or equivalent) with a stable IP. `nat_ip` is required when the deployment uses Cielara's managed RabbitMQ, because the broker's firewall admits exactly that address
        - Address space that does not overlap `172.16.0.0/28` (the Kubernetes control plane range) or the Cloud SQL private services range, `10.96.0.0/16` by default

        A default VPC, such as the `default` network a new project gets, has no secondary ranges or Cloud NAT and does not meet this contract.

Change a machine type only when the region lacks capacity for the default. Types that are too small for a pool are greyed out with the reason.

        |---|---|

There is no on-demand fallback on GCP: if spot capacity runs out, pods wait until it returns. On-demand is recommended for production. |
        | **Agent pool** | Runs the analysis agents. Shown only when your deployment provisions a dedicated agent pool. A spot reclaim mid-run interrupts that agent run, and agent jobs are retried. |

        ### Prepare Your AWS Account

        This step creates the cross-account IAM role Cielara deploys with. No long-lived keys leave your account. You need Terraform 1.7 or later and the AWS CLI, signed in as an IAM admin with `AWS_REGION` set.

        The download is generated for your Cielara account, so take it from your own form rather than reusing a copy.

        1. **Sign in to your cloud.**

           ```bash
           aws sso login
           ```

           If you use static keys instead of SSO, run `aws configure`. Then check the account:

           ```bash
           aws sts get-caller-identity
           ```

           It shows the account you are signed into. The apply prepares that account, so check it is the one Cielara should deploy into.
        2. **Make a folder for this deployment.**

           ```bash
           mkdir -p ~/cielara/<name>/prepare && cd ~/cielara/<name>/prepare
           ```
        3. **Download main.tf into it.** Click **Download main.tf**. The file is pre-filled for your account and region. Then move it into the folder:

           ```bash
           mv <download-folder>/main.tf ~/cielara/<name>/prepare/
           ```
        4. **Apply.** The apply creates the `cielara_eks_deployer` role, trusted only by Cielara's control plane and gated by your Cielara client ID, and writes `cielara-creds.json`.

           ```bash
           cd ~/cielara/<name>/prepare && terraform init && terraform apply
           ```

           By default Terraform keeps its state in this folder. This is not recommended: the state exists only on this machine. Keep it in an S3 bucket you own instead. `main.tf` carries ready-made `backend` blocks: uncomment the one you want before `terraform init`. If you already applied with local state, run `terraform init -migrate-state` after uncommenting it.
        5. **Upload the cielara-creds.json it writes.** It is in `~/cielara/<name>/prepare`. Drop it on **Drop cielara-creds.json here**, or click **Browse**.

        The file fills the role and state location. Click **Enter manually** to see or change them:

        | Field | Description |
        |---|---|
        | **Role ARN** | The ARN of the deployer role, for example `arn:aws:iam::123456789012:role/cielara_eks_deployer`. The account ID in the ARN is the account Cielara deploys into. `terraform output -raw role_arn` prints it. |
        | **Terraform State Storage URL** | Where your prepare run keeps its state: `local`, or a bucket such as `s3://acme-inc-tfstate/cielara-prepare/eks/terraform.tfstate`. Recorded with the deployment so a later update can find the state. |

## Terraform Module Reference

The prepare `main.tf` you download pins a release of Cielara's prepare module for your cloud. The form links to the exact version it pinned under **Module docs**. The full module documentation is on the Terraform Registry:

| Cloud | Module |
|---|---|
| GCP | [cielara-prepare-gke](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-prepare-gke/google/latest) |
| AWS | [cielara-prepare-eks](https://registry.terraform.io/modules/causal-dynamics-lab/cielara-prepare-eks/aws/latest) |

The network `main.tf` pins the same release of Cielara's network module. It also re-exports the module's `handback` output, which is what `terraform output -raw handback` reads. A `main.tf` you write yourself needs the same block, or the command writes an empty file:

```hcl
output "handback" {
  value = module.cielara_network.handback
}
```
